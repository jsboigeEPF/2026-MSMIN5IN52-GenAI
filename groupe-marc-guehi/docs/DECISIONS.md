# Journal des décisions

Format : date — décision — raison — alternatives écartées.

- **2026-10-20 — Architecture cascade STT→LLM→TTS uniquement.** Exigence de l'étudiant ; permet la mesure par étape exigée par le sujet. Écartée : speech-to-speech API Realtime (boîte noire, plus cher). Possible seulement comme baseline externe (voir OPEN_QUESTIONS).
- **2026-10-20 — Client Python local, asyncio pur pour le MVP.** Latence minimale, mesure simple (une horloge). Écartés : navigateur WebRTC/AudioWorklet, FastAPI, aiortc (complexité, hop supplémentaire) ; reconsidérables pour la démo.
- **2026-10-20 — Silero VAD (ONNX, local) dès le MVP.** Nécessaire au barge-in et à l'endpointing, < 1 ms/chunk. Écarté : WebRTC VAD (moins robuste).
- **2026-10-20 — Cloud par défaut : gpt-4o-mini-transcribe, gpt-5-mini (ou nano), gpt-4o-mini-tts.** Coûts très faibles vérifiés. Écartés pour l'instant : Deepgram, ElevenLabs, Cartesia (re-tester si latence TTS/STT insuffisante).
- **2026-10-20 — Local : whisper.cpp ou Parakeet (STT), Qwen3 ~4B 4 bits via mlx-lm/Ollama (LLM), Kokoro (TTS).** Réalistes sur M5 24 Go ; à confirmer par mesure. Piper écarté (archivé), XTTS écarté (MPS cassé).
- **2026-10-20 — Replay audio comme voie principale de mesure.** Reproductible, bruit contrôlé, peu coûteux ; le live sert à la démo.
- **2026-10-20 — Traces JSONL + pandas/matplotlib/Jupyter ; tests pytest + jiwer.** Simplicité.
- **2026-10-20 — Budget interne 10 €, réserve 5 €.** Marge sous la limite de 15 €.
- **2026-10-20 (2) — Interface navigateur (AudioWorklet + WebSocket + FastAPI) remplace le client Python console.** Exigence de l'étudiant (UI agréable). Conséquence : AEC navigateur gratuit, hop WebSocket local à mesurer à part. Remplace la décision « Client Python local ».
- **2026-10-20 (2) — Stack de service : STT = Whisper large-v3-turbo école, LLM = Qwen3.8 Flash (alt. GLM 5.3 Flash / DeepSeek V4.1 Flash), TTS = Qwen-Audio-3.0-TTS Flash (alt. Speech 2.8 Turbo).** Imposé par les accès disponibles (gratuit pour STT) ; remplace les choix OpenAI par défaut. Écartés : API OpenAI directe (pas de clé mentionnée).
- **2026-10-20 (2) — Langue : français ; anglais = piste d'amélioration. Échéance : lundi 2026-10-26, prototype minimal.** Planning compressé (voir ROADMAP).
- **2026-10-20 (3) — LLM = qwen/qwen3.8-27b (réflexion coupée), alt. qwen/qwen3.5-35b-a3b ; remplace Qwen3.8 Flash.** Mesuré : Flash en 429 permanent, GLM 5.3 Flash à raisonnement obligatoire, 27B ≈ 0,4–0,65 s de TTFT. Voir TECH_STACK.
- **2026-10-20 (3) — STT principal : Whisper école, secours : Qwen3 ASR 1.7B (OpenRouter) ; préchauffage obligatoire au démarrage.** Latences équivalentes en régime établi, mais pics de 33–35 s observés sur les deux.
- **2026-10-20 (4) — Boucle testée : Whisper école → deepseek/deepseek-v4.1-flash → Qwen TTS longanhuan_v3.6.** Mesuré (5 tours simulés, script exploratoire retiré du dépôt le 2026-10-24) : latence perçue p50 ≈ 2,6 s (fin de parole simulée 600 ms + STT ≈ 0,6–0,8 s + TTFT DeepSeek ≈ 0,25–0,35 s + TTS 1er octet ≈ 0,5–1,15 s), trop élevée. Leviers à tester (hypothèses) : endpointing plus court, STT spéculatif/16 kHz, 1er chunk TTS plus court, phrase d'accroche pré-synthétisée, TTS local pour le 1er chunk. Préchauffage + connexion réutilisée : STT 2,2 s → 60 ms (audio silencieux), TTS 0,93 → 0,57 s, LLM 0,83 → 0,66 s.
- **2026-10-20 (5) — Optimisation latence mesurée (script exploratoire retiré du dépôt le 2026-10-24, 10 tours/config, réseau réel, fin de parole 350 ms simulée).** Référence p50 2,5 s → A (STT par morceaux 16 kHz + 1er morceau TTS court) p50 2,1 s ; B (A + accroche pré-enregistrée) : 1er son 380 ms mais début de la réponse p50 2,7 s (≈ 0,8 s de silence après l'accroche). Cible 1 s sur le *contenu* non atteignable avec LLM+TTS distants (≈ 1,2 s à eux deux). Pistes suivantes : LLM spéculatif sur transcription partielle, accroches de durée adaptée à l'attente, TTS local (Kokoro) pour le 1er morceau, endpointing ≤ 250 ms.
- **2026-10-20 (6) — TTS : accent chinois signalé sur Qwen (voix longanhuan/loongjohn). Candidat : minimax/speech-2.8-turbo avec voix françaises (French_FemaleAnchor, French_Female_News Anchor, French_MaleNarrator, French_Female_Speech_New, French_Male_Speech_New) — choix de la voix après écoute (`data/voices/report.html`).** Mesuré : TTFB ≈ 400–620 ms (Qwen flash 685–1550 ms sur ce test), WER aller-retour Whisper équivalent (non discriminant pour l'accent). Contraintes : MiniMax ne streame qu'en mp3 (décodage nécessaire) ; les voix françaises natives (Microsoft MAI fr-FR-*, Deepgram Aura-2 *-fr, Mistral Voxtral fr_marie_*, ElevenLabs, Kokoro, Gemini) sont bloquées par une règle de l'espace OpenRouter « teaching-students » de l'école (HTTP 404 guardrail). Plan B : Kokoro local (ff_siwis) sur le M5.
- **2026-10-20 (7) — TTS retenu : minimax/speech-2.8-turbo, voix French_Male_Speech_New et French_Female_Speech_New, une voix tirée au hasard au début de chaque conversation (fixe ensuite).** Validé à l'écoute par l'étudiant. Implémenté : `TTS_VOICES` dans `.env`, `src/tts/voices.py`, `tests/test_voices.py`. Qwen Flash reste en `TTS_MODEL_ALT`.6`) : à ne pas relancer tels quels.
- **2026-10-20 (8) — Étape 2 terminée.** Choix d'implémentation : décodage mp3 progressif avec `miniaudio` dans un thread (pas ffmpeg) car MiniMax génère plus vite que le temps réel ; client HTTP partagé + `warmup()` des 3 briques ; `Recorder` unique pour traces et coûts ; LLM principal = deepseek/deepseek-v4.1-flash, repli qwen/qwen3.8-27b (avant le 1er token seulement). Coût : plafond **indicatif** (avertissement, jamais bloquant, `hard_stop` optionnel) — l'étudiant précise que le budget n'est pas une priorité. Hypothèse non vérifiée : unité du prix TTS = caractère.
- **2026-10-20 (9) — Prototype conversationnel (étapes 3, 4 et 6 en partie).** Navigateur (AudioWorklet 16 kHz PCM16, trames de 512 échantillons) → WebSocket → Silero VAD (ONNX) + `Endpointer` (fin de tour 450 ms, hystérésis 0,5/0,35, pré-roll 300 ms) → `run_turn` (STT → LLM → TTS par morceaux, audio émis dans l'ordre) → PCM 24 kHz planifié par WebAudio. **Demi-duplex** : micro ignoré pendant la réflexion/parole (+0,3 s), faute de barge-in ; la fin de lecture est confirmée par le client (filet de sécurité côté serveur). Mono-utilisateur (un VAD à état partagé). Validé de bout en bout avec les vrais services : micro simulé par WebSocket (2 tours) et dans Chrome via Playwright (micro simulé par fichier WAV, mode texte inclus). Latence perçue mesurée 1,8–2,6 s (non optimisée : ni STT par morceaux, ni accroche). Non testé : vrai micro/haut-parleurs de l'étudiant.
- **2026-10-20 (10) — Retours de l'étudiant + étape 5.** (a) Débit TTS : paramètre `speed` accepté par MiniMax via OpenRouter ; mesuré sur 5 essais par réglage (durée de la phrase test, moyenne) : féminine 8,85 s à 1.0 → 6,62 s à 1.3 ; masculine 7,62 s à 1.0 → 6,67 s à 1.15. Retenu : féminine 1.3, masculine 1.15 (`tts.speeds`). (b) Accroches pré-enregistrées : 12 textes neutres (0,3–2 s) par voix, synthétisées au démarrage puis en cache (`data/fillers/`), silences rognés ; jouées dès la fin de tour si l'énoncé dure ≥ 1,8 s ; choix parmi les 3 plus proches de l'attente moyenne observée (EMA), jamais deux fois de suite la même ; le LLM est prévenu de l'accroche déjà dite ; historique = accroche + réponse. Mesuré (Chrome et WebSocket, vrais services) : premier son ≈ 0,45 s (fin de tour 450 ms), réponse réelle ≈ 1,9–2,1 s, silence résiduel 0–0,37 s. L'accroche masque l'attente, elle ne la réduit pas. (c) Barge-in : duplex, VAD permanent ; pendant que l'agent réfléchit/parle, seuil 0,75 et ≥ 300 ms de parole ; annulation LLM/TTS, `interrupt` au client qui répond `interrupted(played_s)` ; troncature proportionnelle au dernier morceau joué + marque « [interrompu par l'utilisateur] » ; si la phrase interrompue n'était pas encore transcrite, son audio est repris avec la suivante. Limite : la durée jouée inclut les silences d'attente (décalage ≤ ~0,4 s sur la coupe). (d) Keep-alive toutes les 25 s : le Whisper de l'école a mis 2,9 s après quelques minutes d'inactivité. (e) Le harnais de test doit simuler la lecture : MiniMax livre l'audio ≈ 5× plus vite que le temps réel.
- **2026-10-20 (11) — Résultats de la campagne (run1, voix/bruits synthétiques, sans écho, petits n).** STT Whisper : WER ≈ 0 % jusqu'à 5 dB (blanc 0 dB : 16 %, foule 0 dB : 67 %), ≈ 0,45 s. **Foule synthétique : la fin de parole n'est jamais détectée dès 10 dB (50 % à 20 dB)** et déclenche des faux barge-in en direct (4/4 essais foule, 0/1 blanc). Latence (p50/p95) : sans accroche 2,06/2,45 s ; avec accroche : 1er son 0,52 s mais 22 % de réponses prématurées (l'agent démarre avant la fin d'une phrase à pause interne) ; début de réponse ≈ 2,1 s. Fin de tour 450 ms : 20 % de phrases coupées (10 % à 600 ms, 2 % à 800 ms, +≈ 130 ms par palier). Interruptions correctement gérées : 14/21 (67 %) ; arrêt propre 21/21 ; échecs = détection > 800 ms (6, phrase courte « Attends… » : p50 610 ms, p95 1,5 s) et phrase coupée en plusieurs tours (8/21). Balayage hors ligne : seuil VAD 0,5 + 300 ms détecte 100 % des phrases en < 800 ms (médiane 348 ms) contre 83 % aujourd'hui (0,75/300). Corrections de mesure en cours de route : réponses prématurées séparées, transcriptions concaténées pour juger la compréhension, faux positifs comptés comme tels. **Non appliqué** (à décider par l'étudiant) : fin de tour 600 ms, seuil barge-in 0,5–0,6, VAD robuste à la foule.
- **2026-10-21 (12) — Étape 8 : polissage et bilan « terminé ».** UI : étiquettes Vous/Agent, badge « interrompu » sur les réponses coupées, voyant « Voix détectée », médiane de latence de la conversation dans l'en-tête, focus du champ texte après une erreur, mise en page mobile, `prefers-reduced-motion` ; IDs et `window.__stats` inchangés (`browser_smoke.py` vérifié en `VOICE_DRY_RUN=1`, aucune erreur console). `README.md` ajouté (installation, usage, limites). Bilan vs PROJECT_BRIEF : conversation + barge-in + repli texte ☑ (démo au vrai micro à faire par l'étudiant) ; campagne complète ☑ (run1) ; tests 47 verts, ruff propre ☑ ; coût cumulé ≈ 0,47 $ (`data/cost_ledger.jsonl`, 887 lignes) ≪ 15 € ☑. Écarts assumés : bascule automatique vers le texte si le STT échoue, réglages recommandés par la campagne (fin de tour 600 ms, seuil barge-in 0,5–0,6) et mémoire à 5 messages restent non appliqués. Rapport/slides hors périmètre.
- **2026-10-22 (13) — Étapes 3, 4, 6 terminées ; accès internet.** Consigne de l'étudiant : APIs uniquement, aucun modèle local (Kokoro/whisper.cpp écartés). L'anglais ajouté pendant la session a ensuite été retiré (14).
  (b) **Accès internet par function calling** : le LLM dispose de l'outil `web_search` ; s'il l'appelle, un `SearchNotice` part dans le flux, l'orchestrateur joue une accroche « je regarde ça » (pré-synthétisée, par langue/voix), la recherche s'exécute, puis le LLM répond avec le résultat (une recherche au plus par réponse ; requêtes multiples regroupées). Backend de recherche : OpenRouter `/chat/completions` avec le plugin `web` (aucune nouvelle clé). Mesuré (vrais services) : décision d'outil ≈ 0,5–1 s, recherche ≈ 2–3,4 s, ≈ 0,007 $ par recherche ; aucun moteur du plugin n'est nettement plus rapide (défaut, `exa`, `parallel` : 2–3 s). Écartés : outil serveur `openrouter:web_search` (le modèle ne l'appelle pas), `perplexity/sonar` (bloqué par le guardrail de l'école, 404), `engine: native` (non supporté par le modèle). **Défaut trouvé en test réel** : sur une question à deux sujets, DeepSeek écrit l'appel d'outil en texte (balises `<｜DSML｜…>`) au lieu de `tool_calls`, et le TTS le lisait à voix haute ; `ToolMarkupGuard` retient ce texte, en extrait les requêtes et le traite comme un vrai appel. Échec de recherche : le LLM reçoit « SEARCH UNAVAILABLE » et dit qu'il n'a pas pu vérifier. Limite : 2–3 s de silence après l'accroche (mesuré : contenu ≈ 5,5–6,6 s après la fin de parole sur un tour avec recherche) ; la mémoire ne garde que la réponse, pas le résultat brut de la recherche.
  (c) **STT spéculatif** (remplace « STT par morceaux », étape 3) : la transcription part dès 200 ms de silence (`stt.speculative_ms`), avant la fin de tour (450 ms) ; jetée si la parole reprend, réutilisée sinon. Mesuré (Chrome, vrais services) : `stt_final` 416 ms après la fin de tour pour un appel de 677 ms, soit ≈ 260 ms gagnés. Écart avec la piste initiale (transcrire des morceaux pendant la parole) : le serveur Whisper coûte surtout un temps fixe (≈ 0,45 s), découper l'énoncé n'aurait rien gagné de plus.
  (d) **Bascule automatique vers le texte** (étape 6) : STT de secours (`stt.fallback_model` = `qwen/qwen3-asr-1.7b`, OpenRouter) essayé si le Whisper de l'école échoue ; après 2 échecs consécutifs (`stt.fallback_to_text_after`), le serveur envoie `fallback: text`, ignore le micro, la page affiche un bandeau et focalise le champ texte (l'agent répond toujours à voix haute) ; bouton « Réessayer la voix » → `voice_retry`.
  (e) Étape 4 : validée par l'étudiant au vrai micro (« marche très bien en français », 2026-10-22). Tests : 68 verts, ruff propre ; Chrome + vrais services : conversation vocale avec recherche, aucune erreur console.
  (f) **Correction du coût cumulé** : la décision (12) donnait ≈ 0,47 $ en lisant `total_usd` de la dernière ligne ; ce total est propre à chaque processus (la campagne en lançait plusieurs). La somme réelle des `cost_usd` était ≈ 2,14 $ avant cette session, ≈ 2,21 $ après (+ 0,07 $ : recherche, accroches anglaises, tests). Toujours ≪ 15 €. À corriger si on veut un total fiable : sommer le journal, ne pas lire `total_usd`.
- **2026-10-22 (14) — Anglais et détection de la langue retirés ; français seul.** Demande de l'étudiant : tout le code, la config, l'interface et les tests liés à l'anglais (sélecteur de langue, voix `English_*`, profils par langue, détection automatique fr/en) ont été supprimés ; la configuration française est revenue à plat (`llm.system_prompt`, `filler.texts`, `tts.speeds`), complétée par `llm.date_line`, `llm.search_hint`, `filler.search_texts`, `stt.language`, `search.language`. **Faits vérifiés (2026-10-22) à ne pas re-chercher si l'anglais revient** : `minimax/speech-2.8-turbo` accepte 11 identifiants `English_*` via OpenRouter (dont `English_Trustworthy_Man`, `English_Graceful_Lady`, `English_expressive_narrator`, `English_Persuasive_Man`, `English_CalmWoman`), un identifiant bidon est refusé en 502 ; les STT (Whisper de l'école, Qwen3 ASR avec `response_format=verbose_json`) renvoient la langue détectée sans qu'on l'impose, mais **sur énoncés très courts la détection se trompe** (« Yes. » → fr et traduit « Oui. », « Non. » → it, « Stop. » → pl ; fiable sur énoncés ≥ 1,2 s) ; l'accroche part avant la fin du STT, donc elle serait dans l'ancienne langue au tour d'un changement de langue. Le journal de la session (étape 13) reste valable pour la recherche, le STT spéculatif et la bascule texte.
- **2026-10-24 (15) — Étape 10 : attente de recherche, secours, bascule texte.** Demande de l'étudiant (3 priorités). Consigne confirmée : secours **API uniquement**, rien d'installé en local.
  (a) **L'agent dit ce qu'il cherche** : l'outil `web_search` a un 2e paramètre obligatoire `announce` (phrase de 4 à 9 mots écrite par le LLM, ex. « Je regarde la météo à Lausanne. »). La session la synthétise **en tâche de fond pendant la recherche** (elle ne retarde pas la recherche) et la joue avant la réponse ; elle est gardée dans l'historique, et mise dans le message `tool_calls` pour que le LLM ne la répète pas. Si le TTS échoue ou si le LLM n'a pas rempli `announce` (balises DSML), repli sur l'accroche générique pré-enregistrée. **2e phrase** (« Encore un instant. », `filler.search_wait_*`) si, `filler.search_wait_after_s` = 3 s après l'avis de recherche, la réponse n'a pas commencé. Écarté : lire la requête brute (`météo Lausanne 2026-10-24` sonne mal à l'oral). Mesuré (vrais services, `ws_client`, « météo à Lausanne ») : l'annonce démarre ≈ 1,7 s après la fin de transcription (décision d'outil du LLM + 1er octet TTS), recherche 3,1 s, 2e phrase à 8,1 s, début de réponse 8,5 s ; un seul essai, p50/p95 à mesurer. Limite : le silence avant l'annonce (≈ 1,7 s) reste.
  (b) **Secours en cas de panne d'API** : STT (déjà : Whisper école → Qwen3 ASR) ; LLM (déjà : `LLM_MODEL_ALT` avant le 1er token) ; **TTS nouveau** : `FallbackTTS` bascule sur `TTS_MODEL_ALT` (`qwen/qwen-audio-3.0-tts-flash`, PCM, voix `tts.fallback_voice`) si MiniMax échoue **avant le 1er octet** (pas de changement de voix en plein morceau). Vérifié avec les vrais services : secours seul 2,4 s d'audio, 1er PCM ≈ 1,1 s ; MiniMax forcé en 401 → secours utilisé. Dernier recours : si tout le TTS échoue, le tour continue (`tts_error`), le texte reste affiché, le serveur envoie `tts_down` et l'interface le signale. Accroches pré-enregistrées : toujours avec la voix principale (le cache est rangé par modèle/voix). Limite : accent chinois de la voix de secours (voir TECH_STACK) ; si OpenRouter lui-même est en panne, tout tombe (même fournisseur).
  (c) **Bascule vers le mode texte testée en réel** : injection de panne `VOICE_FAIL_STT=1` (STT principal et secours en échec), `scripts/browser_fallback_test.py` dans Chrome (micro simulé, 2 énoncés) : bandeau affiché, champ texte actif, micro coupé, saisie clavier → réponse **avec audio**, « Réessayer la voix » rétablit la voix ; aucune erreur console. Reste non testé : une vraie coupure réseau du serveur Whisper de l'école.
  (d) Tests : 79 verts, ruff propre.
